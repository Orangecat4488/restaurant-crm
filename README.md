# Restaurant CRM — Multi-Service, Multi-Tenant, Production-Hardened

Three independent services that together form a restaurant CRM with commercial licensing.

```
+-----------------------------+
|  ADMIN PANEL  (:5173)       |   /api → :5000  (admin-api)
|  Seller dashboard,          |
|  issues licenses,           |
|  manages clients            |
+-----------------------------+
              |
              |  issues / revokes license keys
              v
+-----------------------------+   /api → :5001  (restaurant-api)
|  RESTAURANT CRM  (:5174)    |   <-- licenseGuard blocks all /api/restaurant/*
|  POS terminal UI,           |       when license is expired / revoked
|  menu, orders, staff        |
+-----------------------------+

+-----------------------------+   /api → :5002  (storefront-api)
|  CUSTOMER STOREFRONT (:5175)|   <-- plans, checkout, Stripe webhook,
|  Plans, checkout,           |       license generation
|  license delivery           |
+-----------------------------+
```

## Multi-tenant & auth isolation invariants

The system enforces, at both the backend and the frontend, that:

1. **Per-account brute-force protection.** Lockouts are scoped to a single
   email (account) only. User A's failed attempts NEVER block User B.
   Implementation: `login_attempts` table with `UNIQUE(email)`. The
   lockout duration is a single, hard-coded constant
   `LOCK_DURATION_SECONDS = 60` in `backend/src/utils/bruteForceGuard.ts`.
2. **Per-user license cache.** The frontend license store persists state
   under a per-user key. User A's license never bleeds into User B's
   session. On logout, the per-user slot is wiped atomically.
3. **Per-user device fingerprint.** A single
   `crm_device_fingerprint` localStorage value is read by both the auth
   and license stores. The fingerprint is audit-only and is NOT part of
   any lock key.
4. **Server-issued lockout countdown.** The frontend never computes
   remaining lock time itself. The backend returns `retryAfter` and
   `lockedUntil`; the client trusts those values verbatim and renders a
   countdown derived only from `lockedUntil - Date.now()`.
5. **Tenant isolation on the backend.** All authorization decisions
   derive the actor from the signed JWT (`req.user.userId`,
   `req.user.clientId`). The backend NEVER trusts a `clientId` /
   `tenantId` coming from the request body.
6. **License enforcement on the server.** The `restaurant-api` mounts a
   `licenseGuard` middleware in front of every `/api/restaurant/*`
   route. A revoked / expired license returns `402 LicenseExpired` even
   if the JWT is still valid. The frontend LicenseGuard is a UX
   convenience, not the security boundary.

## Brute-force protection (Test matrix A–E)

See `backend/src/modules/auth/__tests__/auth.bruteforce.test.ts`:

| A | A wrong × 5 | A locked 60s; B, C unaffected |
| B | A wrong × 5, B wrong × 5 | A locked 60s, B locked 60s, C unaffected |

## Brute-force lock: per-account, exactly 60 seconds (both backends)

Both backends enforce the same invariant:

- **restaurant server (`server/`)**: the lock lives on the user row
  (`locked_until`), constants `MAX_FAILED_LOGIN_ATTEMPTS = 5` and
  `LOGIN_LOCK_DURATION_SECONDS = 60` in `server/src/models/user.ts`. The
  5th wrong attempt is answered with `423 AccountLocked` carrying a
  server-issued `retryAfter` and `lockedUntil` (+ `Retry-After` header).
- **licensing platform (`backend/`)**: `login_attempts` table keyed by
  `UNIQUE(email)`, constant `LOCK_DURATION_SECONDS = 60` in
  `backend/src/utils/bruteForceGuard.ts`.
- The auth rate limiter in `server/src/middleware/security.ts` is keyed by
  **account email** (never IP-only) — one user's failures can never lock
  out another user on the same IP.
- After a successful login the counter is reset **only** for that account.
- Expired/corrupt locks are auto-cleaned on the next check (stale-record
  safety), and a lock never escalates: it is always exactly 60s.

```bash
cd server && npm run dev     # :3001 (SQLite)
npm run dev                  # root: POS frontend :5173 (proxies /api → :3001)
```

## License lock duration: 60s, no exceptions

`backend/src/utils/bruteForceGuard.ts` exports a single
`LOCK_DURATION_SECONDS = 60` constant. Both the lock creation logic
and the test suite reference this constant directly. The previous
env-var based configuration (`BRUTE_FORCE_LOCK_TIME`, in minutes) was
the source of the 772/773s values reported in the audit because
different code paths interpreted the value in different units; that
configuration is now removed from the login code path.
